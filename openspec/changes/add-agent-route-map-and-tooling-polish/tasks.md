Each task is one factory run and one PR. Run the tooling gate (`npm run test:tooling`, `npm run lint`) for every task.

## 1. Tooling

- [x] 1.1 Add `scripts/route-map.js` and `scripts/route-map.test.js`, and add the test to `test:tooling` in the root `package.json`. The script reads the `MINIMAL_API_ROUTES` table in `workers/src/index-minimal.ts` and prints one line per entry: `METHOD<TAB>path-or-pattern<TAB>handler<TAB>file:line`, where `file:line` is the handler's definition in `workers/src/` (a `function`, `async function` or `const` declaration, following the `import` in `index-minimal.ts` to its module first). Test files (`*.test.ts`, `*.spec.ts`, anything under `__tests__/` or `test/`) are never searched, so a mock with the handler's name cannot be reported. A path held in a `RE_*` constant prints as that constant's regex source, and an inline regex literal prints as written. An entry the script cannot parse (for example one split over several lines in a shape it does not handle, or a handler it cannot locate) makes it exit non-zero and name the entry; it never skips one silently. Add a root script `"route-map": "node scripts/route-map.js"` and a two-line pointer to it in `workers/README.md` under "Request pipeline".
      Acceptance: the test runs the script on the real `workers/src/index-minimal.ts` and asserts that it prints one line per table entry, that every `file:line` exists and declares the named handler, and that `GET /api/products` maps to `handleGetProducts`. A unit test on a small fixture covers an inline path, a `RE_*` pattern, an inline regex literal, an entry split over several lines, an imported handler, a test-file decoy with the same handler name (not reported), and an unparseable entry (non-zero exit). The script does not modify any file.
