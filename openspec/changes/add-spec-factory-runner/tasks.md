## Phase 1 — One task, started by hand

- [x] 1.1 Add `.claude/skills/run-spec/SKILL.md`. It runs `/resume <id>`, implements exactly one unchecked task, gates, pushes, opens a PR labelled `factory:<id>`, ticks the task, and updates `handover.md`. It refuses operator tasks with `needs-human`, and before pushing runs `scripts/check-no-go.js`, which fails if `git diff --name-only --no-renames origin/main...HEAD` (merge base, not the moving tip; both sides of a rename) matches a `no_go` pattern. The patterns are a hard-coded baseline (`.github/**`, `database/migrations/**`, `scripts/database-backup.sh`, `scripts/check-no-go.js`, `.claude/**`, `AGENTS.md`, `CLAUDE.md`) plus the change's own `no_go` entries, which add to the baseline and never replace it.
      Acceptance: the skill names every step above; `check-no-go.js` has tests for matching and non-matching paths, for a rename out of a protected path, and for a change whose `no_go` list omits `.github/**` still failing on a workflow edit.
- [x] 1.2 Add `.github/workflows/factory.yml` with a `workflow_dispatch` input `change_id`. It runs `claude-code-action@v1` with `prompt: /run-spec <change_id>`, with no production secrets, token permissions limited to contents, pull-requests and issues write plus `id-token: write` (required for the action's OIDC login) and `actions: read` (for `gh run view --log-failed`), and `--disallowedTools` for `Bash(gh pr merge:*)`, `Bash(gh pr review:*)` and `Bash(gh api:*)`. New-task runs share the concurrency group `factory-<change_id>` with `cancel-in-progress: false`, and `run-spec` exits without changes when an open `factory:<id>` PR already exists.
      Acceptance: the workflow passes `actionlint` locally; a static test asserts it references no `prd`, `PRODUCTION` or `NEON_API_KEY` secret, carries the deny-list, sets the per-change concurrency group, and grants no permission beyond those five.
      Done: actionlint 1.7.7 clean; `scripts/factory-workflows.test.js`. The prompt names the skill in words instead of `/run-spec`, which may not resolve as a slash command in agent mode. In agent mode the action allows no Bash unless listed, so the workflow also carries an `--allowedTools` list.
- [x] 1.2a Add `.github/workflows/no-go-guard.yml` on `pull_request_target`. It uses `main`'s `scripts/check-no-go.js`, never checks out PR code, reads the file list from the pulls files API, including each `previous_filename`, reads the change's `no_go` entries from `main`'s copy of its `proposal.md`, and fails factory PRs (label `factory:*` or Claude App author) that touch a `no_go` path. Owner adds it to the `main` ruleset's required checks.
      Acceptance: a static test asserts the trigger is `pull_request_target` and that no step checks out the PR head; a test PR touching `.claude/**` fails the check.
      Built: the workflow and its static test. The result is posted as the commit status `factory/no-go-guard` on the PR head, since a `pull_request_target` check run is attached to the base commit; that status is what the ruleset requires. The guard applies every active change's `no_go` list (`--change all`), not the one a `factory:<id>` label names, because the factory can edit its own PR's labels. Consequence: while a change is active, its list protects those paths from every factory PR; archive a change to lift it. Verified 2026-10-23 on throwaway PR #689 (label `factory:test`): `failure` with `.claude/no-go-guard-test.md`, `success` after the file moved to `docs/`.

## Phase 2 — Chain and babysit on events

- [x] 2.1 Add a `pull_request: closed` trigger: when a `factory:<id>` PR merges, start the next task.
- [x] 2.2 Add `pull_request_review`, `pull_request_review_comment` and `workflow_run: completed` (listing the CI workflows; `check_suite` does not fire for Actions-created suites) triggers that run one `babysit-pr` pass for `factory:<id>` PRs. Use `allowed_bots: sentry[bot],codescene-delta-analysis[bot],copilot-pull-request-reviewer[bot]`, and a concurrency group per PR. Give `babysit-pr` a one-shot mode for the runner: it never waits, watches or schedules a check-back, and it ignores the quiet window (each late bot review starts its own pass). It exits without changes only while a GitHub Actions check is pending, because that check's `workflow_run: completed` event starts the next pass. Pending checks from other apps (CodeScene, Seer) do not hold the pass: they emit no `workflow_run`, and their results arrive as reviews, which start passes of their own. Add the check's `workflow` to `fetchChecks` in `pr-feedback.js` so the pass can tell the two apart (`gh pr checks` leaves `workflow` empty for non-Actions checks). Otherwise it acts on every actionable item. Update `babysit-pr` so each pass runs `scripts/check-no-go.js` before pushing, adds a `Babysit-Round: N` trailer to its commits, and stops with `needs-human` once the PR's highest trailer reaches 5. While editing `babysit-pr`, also have it log `node scripts/pr-feedback.js <n> --summary` (added by the pilot, #693) as the one-line state of each pass; the pilot left this to the owner because `.claude/**` is protected.
      Acceptance: a static test asserts the concurrency group and the bot allowlist; a test for the round reader covers no trailers, rounds 1–4, and 5; a `pr-feedback.js` test shows a pending non-Actions check does not count as an Actions check still running.
      Done: `scripts/factory-route.js` (the `route` job) decides task, babysit or nothing for each event, and skips events with nothing to act on, with Actions checks still running, with a `needs-human` label, or on an archived change, before any Claude run starts. Only PRs authored by the Claude App and labelled `factory:<id>` count. `scripts/babysit-round.js` reads the trailers. The route job checks out `main`, and the run job restores `main`'s skills and factory scripts over the PR branch, so a factory PR cannot steer its own passes; the new scripts are on the `no_go` baseline. `babysit-pr` has a one-shot mode and logs `--summary`; `run-spec` reports a finished change instead of guessing.

      Acceptance: every task after the first starts from the merge trigger (2.1), every review or CI fix comes from a one-shot babysit pass (2.2), and the run, PR and fix-round count for each task are recorded in `handover.md`.
