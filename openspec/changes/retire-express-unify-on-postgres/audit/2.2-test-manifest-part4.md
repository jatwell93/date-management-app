## Two findings that govern every `tenant-isolation` row below

These were established before any row was written, because both change how the evidence in this
file must be read. Neither is a defect introduced by this change; both are pre-existing facts
about the Worker suite that only become load-bearing at Phase 4 deletion.

#### Finding 1 — `workers/src/__tests__/multi-tenant-isolation.test.ts` asserts nothing

All 8 of its tests have the same body: a prose comment describing a scenario, then
`const expected = true; expect(expected).toBe(true)`. The file passes, is counted by the runner,
and constrains no behaviour. It is not alone — 90 such tests exist across 8 Worker files, and
`workers/src/handlers/handlers.test.ts` is likewise 20/20:

| Worker file | Tautological / total |
|---|---:|
| `__tests__/multi-tenant-isolation.test.ts` | 8 / 8 |
| `handlers/handlers.test.ts` | 20 / 20 |
| `__tests__/org-status-integration.test.ts` | 16 / 19 |
| `__tests__/error-handling.test.ts` | 19 / 28 |
| `__tests__/auth-integration.test.ts` | 14 / 18 |
| `__tests__/subscription-validation.test.ts` | 7 / 14 |
| `__tests__/usage-limits-integration.test.ts` | 4 / 13 |
| `__tests__/feature-gates-integration.test.ts` | 2 / 8 |

Because its **name** is the most plausible thing to cite as the Worker equivalent of the
backend's tenant-isolation gate, citing it as positive evidence would retire a real gate against
a test that cannot fail. **No row in Parts 1–3 does this** — all 345 citations of these files
across the merged manifests appear inside negative evidence ("searched X, none found"), which is
correct use. `scripts/verify-audit-manifest.js` now fails the build on the positive form, so the
property is enforced rather than merely observed.

#### Finding 2 — the Worker's *real* isolation coverage is not run by CI

The genuine cross-tenant assertions live in the pglite/conformance suites — real SQL, real
seeded `org-b` rows, real expectations:

- `workers/src/database.dashboard.pglite.node.test.ts:110` — "scopes counts to the requested
  organization"; seeds two `OTHER_ORG` items and asserts `expiringItems` is 1, not 3.
- `workers/src/database.dashboard.pglite.node.test.ts:161` — an `OTHER_ORG` loss of 500 is
  excluded from a 150 total.
- `workers/src/database.dashboard.pglite.node.test.ts:213` — "ignores other organizations and
  returns null when none completed".
- `workers/src/database.report.pglite.node.test.ts:82-87` — `org-b` rows in the same windows must
  not inflate `org-a` counts.
- `workers/src/database.supplier-policy.conformance.node.test.ts:237` — asserts organization
  isolation alongside status and ordering.

These are cited below as real equivalents. **But `npm run test:db` and the workers vitest pool run
in no CI workflow** (no `.github/workflows/*` references either), so the coverage that survives
Phase 4 deletion is coverage nothing enforces on a pull request. That is a separate problem from
this manifest's, and it is recorded here so the `worker-equivalent-exists` rows below are not read
as stronger than they are.

### integration/multi-tenant-penetration.test.ts

The backend's `penetration` gate: 20 supertest-driven attack simulations against the real Express
app with a real Prisma client, in three groups — injection/IDOR/mass-assignment (9), JWT
validation (6), and route-parameter tampering (5).

**Read the assertions before trusting the file name.** Several tests in the first group send **no
`Authorization` header at all**, so the 403 they assert is the unauthenticated-request path and
the tampering they are named for is never exercised (`:248`, `:321`, `:395`). Others assert a
disjunction satisfied either way — `:196` and `:274` accept *any* status >= 400 *or* an empty
200 body, and `:457` accepts `[200, 403, 500]`, so a 500 passes a test named "should accept valid
JWT". These are recorded per row; where a test does not constrain the behaviour it names, that is
stated rather than carried forward as coverage.

**The Worker's structural position matters for every `org_id`-tampering row.** In
`workers/src/index-minimal.ts` there is exactly **one** assignment of an organization identifier —
`const organizationId = auth.organizationId` at `index-minimal.ts:3352`, taken from the verified
JWT. No route parameter, query string, or request body is ever read into it. The attack surface
these tests probe is therefore *absent by construction* in the Worker, not merely untested — the
same positive-evidence standard applied to the Clerk-managed invite rows in Part 2, rather than
the weaker "no Worker analogue found" argument.
