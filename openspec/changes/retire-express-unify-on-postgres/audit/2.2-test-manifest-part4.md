#### Finding 3 — a cross-tenant leak on the *write* path, found by auditing the two rows above (#466)

Added after Findings 1 and 2, when the two `worker-shaped-rewrite` rows for cross-tenant
UPDATE/DELETE were worked. Those rows predicted a mutation keyed on id alone; the mutations turned
out to be correctly scoped. The defect was one layer over:

`updateInventoryItem` validated that a supplied `locationId` belonged to the caller's organization
but did **not** validate `productId` — while `createInventoryItem` validated **both**. Meanwhile 20
JOINs across `database.ts` resolved `products`, `store_areas` and `inventory_items` by id alone,
without correlating on organization (`JOIN products p ON ii.product_id = p.id`). The two compose:

```
PATCH /api/inventory-items/{own_id}   {"productId": <victim's product id>}   -> 200 OK
GET   /api/reports/loss-by-sku                                               -> victim's sku, name, cost_price
```

Product ids are `SERIAL`, so the victim id is enumerable. Confirmed by real-SQL test, not by
inspection: the update returned the item with the foreign `productId`, and `getLossBySkuReport`
for the attacker's organization then returned `SKU-SECRET` — a row belonging to another tenant.

Fixed on both sides, because either alone leaves a hole: the missing `productId` check (which stops
the bad reference being created) and all 20 uncorrelated JOINs (which stop any pre-existing or
future bad reference being resolved). Verified by mutation — removing the `productId` check fails
exactly one test, removing the JOIN correlation fails exactly two.

**Why this matters for the manifest method.** A `worker-shaped-rewrite` row is a claim that a
property is untested, and the natural way to close one is to write the test and move on. Here,
writing the test is what surfaced a live vulnerability that no Express row described — the Express
suite has no equivalent, because Prisma's service-scoped constructor makes the reference-repointing
shape hard to express. Rows should be worked by exercising the Worker against real SQL, not by
reading the Worker and judging it equivalent.

**One deliberate exception, recorded so it is not "fixed".** `reviewCatalogueCorrection` is the
only mutation in `database.ts` with no organization predicate, and it is correct: catalogue
corrections are reviewed by a **platform** admin across all tenants, gated by `isPlatformAdminUser`
rather than tenant membership. A sweep for "mutations missing `organization_id`" flags it first and
the guard that justifies it lives in another file, so the reasoning is now a comment at the method.

#### Finding 4 — the Worker enforces no usage limit on any interactive path

Established while working the `concurrency` and `feature-limits` files. Unlike Findings 1–3 this is
**not fixed** — it is a parity gap for Phase 3.1 to close, recorded here because it governs every
`feature-limits` and `concurrency` row below and would otherwise be rediscovered three times.

Three independent facts, each enumerable rather than judged:

1. **`workers/src/utils/feature-gates.ts` has no production importer.** A repo-wide search for the
   module path across `workers/src/**` outside `*.test.ts` returns **nothing**. Its five exports
   (`checkFeatureAccess`, `checkUsageLimit`, `requireFeatureAccess`, `enforceUsageLimit`,
   `formatUsageLimitCTA`) are referenced only by `utils/feature-gates.test.ts`,
   `__tests__/feature-gates-integration.test.ts`, and `__tests__/usage-limits-integration.test.ts`.
   The module is dead code carrying a 362-line test suite.

2. **Its SQL cannot run against the schema.** `checkUsageLimit` queries `"Product"`, `"User"`,
   `"InventoryItem"` and `"Upload"` — quoted PascalCase Prisma table names — while the Postgres
   schema uses `products`, `users`, `inventory_items`, `uploads`. Exercised against pglite, every
   branch throws and falls into the catch:

   ```
   [FeatureGate] Error checking usage limit: error: relation "Product" does not exist
   PROBE max_skus => {"isWithinLimit":false,"currentUsage":0,"limit":5000,"error":"Failed to check max_skus limit"}
   [FeatureGate] Error checking usage limit: error: relation "User" does not exist
   [FeatureGate] Error checking usage limit: error: relation "Upload" does not exist
   ```

   The module fails closed, so wiring it up as-is would reject every create. Its own test suite
   passes because it supplies a mock `dbClient` returning canned rows, which never validates SQL —
   the same class of defect as Finding 1, one layer down: a test that exercises a query string
   nothing will ever execute.

3. **The one inline gate reads a counter nothing maintains.** `POST /api/users`
   (`index-minimal.ts:2673`) does check `max_users`, against `organization_usage`. But
   `organization_usage` is written in exactly one place in the entire Worker — a lazy
   `INSERT ... ON CONFLICT DO NOTHING` of literal zeros inside `handleGetOrganizationUsage`
   (`index-minimal.ts:3084`), seeding `active_users` 0, `max_users` 1, `total_skus` 0. There is no
   `UPDATE organization_usage` anywhere, and no database trigger (no `CREATE TRIGGER` exists in any
   migration). So `active_users` is permanently `0`, the guard `activeUsers >= maxUsers` evaluates
   `0 >= 1` → false, and the limit **never fires**. The same staleness makes
   `GET /api/organization/usage` report `total_skus: 0` for every organization regardless of
   catalogue size.

`POST /api/products` (`handleCreateProduct`, `index-minimal.ts:2266`) performs no limit check at
all. The **only** working usage enforcement in the Worker is on the bulk catalogue-import path,
where `isCatalogueWithinLimit` (`upload/catalogue-import.ts:114`) compares a projected SKU count
against the `max_skus_snapshot` captured at job creation from `LAUNCH_TIER_LIMITS`
(`index-minimal.ts:3980`) — a separate mechanism that does not consult `organization_usage` and
does not cover interactive creates.

None of this is a tenant-isolation defect: no organization can reach another's data through it.
It is a revenue-and-capacity gap, and it means **no `feature-limits` row below may be resolved
`worker-equivalent-exists` on the strength of `feature-gates.ts`.**

### integration/multi-tenant-penetration.test.ts

The backend's `penetration` gate: 20 supertest-driven attack simulations against the real Express
app with a real Prisma client, in three groups — injection/IDOR/mass-assignment (9), JWT
validation (6), and route-parameter tampering (5).

**Read the assertions before trusting the file name.** Several tests in the first group send **no
`Authorization` header at all**, so the 403 they assert is the unauthenticated-request path and
the tampering they are named for is never exercised (`:248`, `:321`, `:395`). Others assert a
disjunction satisfied either way — `:196` and `:274` accept *any* status >= 400 *or* an empty
200 body, and `:457` accepts `[200, 403, 500]`, so a 500 passes a test named "should accept valid
JWT". These are recorded per row; where a test does not constrain the behaviour it names, that is
stated rather than carried forward as coverage.

**The Worker's structural position matters for every `org_id`-tampering row.** In
`workers/src/index-minimal.ts` there is exactly **one** assignment of an organization identifier —
`const organizationId = auth.organizationId` at `index-minimal.ts:3352`, taken from the verified
JWT. No route parameter, query string, or request body is ever read into it. The attack surface
these tests probe is therefore *absent by construction* in the Worker, not merely untested — the
same positive-evidence standard applied to the Clerk-managed invite rows in Part 2, rather than
the weaker "no Worker analogue found" argument.

### integration/multi-tenant-concurrency-load.test.ts

Nominally the backend's `concurrency` gate: six tests firing 10–100 simultaneous writes at an
organization sitting on a tier boundary, to prove limits hold under races.

**None of the six exercises application code.** Every operation is a direct `prisma.product.create`,
`prisma.user.create`, or `prisma.organizationUsage.update` issued by the test body itself. No
service, no controller, no route, no feature-gate middleware is on the path. The file's own comments
say so at `:110`, `:185`, `:436` and `:523` — *"Direct Prisma writes bypass feature-gate
enforcement"* — and the assertions were then written to match that reality rather than the test
names.

The result is a variant of Finding 1 worth naming separately, because it is not tautological and so
does not show up in a `expect(true).toBe(true)` sweep. These tests are **inverted**: the assertion
codifies the very outcome the name promises to prevent. `should prevent SKU overshoot under extreme
concurrent load` seeds 490 SKUs against a 500 cap, fires 100 concurrent creates, and asserts
`expect(finalCount).toBe(590)`. The test passes *because* the limit was exceeded, and would fail if
enforcement were ever added. It is not a gate; it is a regression test against having one.

Consequently **no row here can be retired "in favour of" Worker coverage, and none can be carried
forward as a preserved gate** — there is no gate to preserve. What must survive into Phase 3.2 is
the *property* each test is named for, none of which this file establishes and, per Finding 4, none
of which the Worker currently enforces either. Each row below therefore records the Express test as
`retire` (it constrains nothing) while naming the property in the Evidence cell so 3.2 has the list.

**Every Stripe row targets a Worker surface that does not exist.** The Worker handles Clerk

no `stripe` import anywhere in `workers/src` outside a CSP directive in
`middleware/security-headers.middleware.ts` and an unrelated string in `utils/auth.ts`. So these
rows are not "untested in the Worker" — they are unimplemented, and the manifest's job is to make
sure the Stripe handler is built against this list rather than from scratch.

**Finding 5 — the Worker's one webhook idempotency mechanism is check-then-act, and untested.**
Established by working the two duplicate-event rows (`:183`, `:199`) against the Clerk handler,
which is the only webhook the Worker has and therefore the template the Stripe handler will copy.
`handleClerkWebhook` (`clerk/webhook-handler.ts`) runs three unrelated statements with no
transaction:

```
isNewClerkWebhookEvent(sql, svixId)   -> SELECT ... WHERE id = $1   (true)
processClerkWebhookEvent(sql, event)  -> all side effects
markClerkWebhookEventProcessed(...)   -> INSERT ... ON CONFLICT (id) DO NOTHING
```

Two concurrent deliveries of the same Svix event both observe `isNew === true`, because the marker
is written *after* processing. The `ON CONFLICT` deduplicates the marker row, not the work. Svix
delivers at-least-once and retries on timeout or 5xx, so concurrent redelivery is the expected case,
not a pathological one.

It is also not harmless. `ensureTrialSubscription` (`clerk/clerk-persistence.ts:97-102`) is itself a
check-then-insert — `if (existing.length > 0) return;` followed by an `INSERT INTO
subscription_tiers` with **no** `ON CONFLICT` — so a doubled `organization.created` delivery can
write two `trialing` rows for one organization.

A repo-wide search for `isNewClerkWebhookEvent`, `markClerkWebhookEventProcessed` and
`clerk_webhook_events` across `workers/src/**/*.test.ts` returns **nothing**. The mechanism has no
coverage at all. Recorded as a Phase 3.1 defect in its own right, separate from the Stripe work,
and as a constraint on it: the Stripe handler must not copy this shape.

genuine. The rule under test is the standard OWASP mitigation — a cell whose first character is
`=`, `+`, `-` or `@` (after stripping a leading tab or carriage return) is prefixed with an
apostrophe, so a spreadsheet renders it as text instead of evaluating it.

**The Worker does not implement this.** Checked directly: a search across all of `workers/src` for
any formula-escaping construct returns nothing, and the Worker's own parser handles the same three
fields the backend sanitizes —

```
workers/src/upload/catalogue-parser.ts:93-95
  const sku     = (row[columnIndexes.sku] || '').trim();
  const name    = (row[columnIndexes.name] || '').trim();
  const barcode = (row[columnIndexes.barcode] || '').trim();
```

`.trim()` is the whole of it. The values go on to `products` and `master_catalogue_entries` raw.

**Framed precisely, because the distinction matters for a deletion gate.** This is not a live
exploit in the Worker: the Worker has no CSV *export* route, and its only download path serves a
JSON error report (`index-minimal.ts:3843`). The finding is that **cutting over to the Worker
removes a control that exists today.** Sanitization belongs at ingestion exactly because the export
that weaponizes the payload need not live in the same service — the Express product-export path and
the frontend both read these columns, and a stored `=HYPERLINK("http://evil.com","Click here")` in a
product name is inert in the database and dangerous the moment anything writes it to a spreadsheet.
Retiring these rows on "no Worker export route exists" would be reasoning from the absence of one
half of a two-part vulnerability.

**Twelve rows for one rule.** Tests `:74` through `:107` are payload variations on the same
leading-character check — command strings, DDE, hyperlinks, extended characters — rather than
distinct behaviours. They are recorded individually because the manifest's contract is one row per
test, but the Evidence cells say which are variations, so Phase 3.2 reproduces one parametrised gate
with a representative corpus rather than twelve separate tests.

## A note that governs every `contract/` row below

The five files in `backend/src/tests/contract/` are 167 lines in total and are the thinnest in Part
4. Before any of their rows can be read, one fact about how they run:

```
backend/src/tests/setup-env.ts:8
  process.env.TEST_AUTH_BYPASS = process.env.TEST_AUTH_BYPASS || 'true';
```

That file is the suite-wide setup. `TEST_AUTH_BYPASS` therefore defaults to `'true'` for **every**
backend test unless a test overrides it, and `auth.middleware.ts:129` short-circuits to a synthetic
`default-org` Manager whenever it is set under `NODE_ENV=test`. So a contract test that issues an
unauthenticated request and asserts `200` is asserting **route shape only** — it cannot and does not
constrain authorization. `contract/auth.test.ts` is the sole file here that flips the flag
deliberately, which is why it is the only one with an authorization row.

**Finding 7 — the bypass helper and the bypass guard disagree.** Adjacent to the above, and worth
recording because it is the shape that produced #462 and #466:

| Location | Predicate |
|---|---|
| `middleware/auth.middleware.ts:129` | `NODE_ENV === 'test'` **and** `TEST_AUTH_BYPASS === 'true'` |
| `middleware/clerk-auth.middleware.ts:79` | `NODE_ENV === 'test'` **and** `TEST_AUTH_BYPASS === 'true'` |
| `utils/auth-bypass.ts:11` (`isTestEnvironment`) | `NODE_ENV === 'test'` **or** `TEST_AUTH_BYPASS === 'true'` |

Both middlewares use a conjunction; the helper that shares their vocabulary uses a disjunction. The
helper backs `getOrganizationId(organizationId?)` (`auth-bypass.ts:18-28`), which returns the literal
`'default-org'` rather than throwing whenever no organization id is supplied *and* the predicate
holds. Eight services take their entire tenant scope from it — `product.service.ts:101`,
`inventory.service.ts:83`, `csv-parser.service.ts:226`, `store-area.service.ts:29`,
`credit-claim.service.ts:132`, `markdown-config.service.ts:62`, `supplier-credit.service.ts:174`,
and `service-provider.ts:46` — and `ServiceProvider.withClients(prisma)` (`:64`) reaches it with
`organizationId` undefined by design.

Severity is bounded and stated honestly: reaching it requires `TEST_AUTH_BYPASS=true` under a
non-`test` `NODE_ENV`, which is a deployment mistake rather than a request an attacker can make, and
Express is not the deployed system. It is recorded because it is a silent cross-tenant *fallback*
where the two sibling guards fail closed, and because it means **no row in this file may cite a
service constructor as evidence that tenant scoping is enforced** unless the test passes an explicit
`organizationId`. The Worker has no counterpart: `index-minimal.ts:3352` is the sole assignment of
`organizationId` and it reads the verified JWT, with no fallback branch.

### services/org-bootstrap.service.test.ts

Twelve tests against a real `PrismaClient` (`:5`) with only `SubscriptionService` mocked (`:26-29`).
No route, no HTTP — it drives `OrgBootstrapService.bootstrap()` directly and then reads the rows back

**The Worker's counterpart is stronger, not weaker,** which is unusual here and worth stating up
front. `workers/src/clerk/bootstrap-handler.node.test.ts` drives `handleOrganizationBootstrap` end to
end against **real SQL on pglite** — request in, `Response` out, rows asserted afterwards — across
four tests covering the returning-user, existing-org, and brand-new-org paths. Most rows below
therefore resolve `worker-equivalent-exists` against a test that is closer to production than the
Express original.

Two things do not survive, and they are unrelated to each other.

**Finding 8 — the organization RBAC audit trail has no table in the Postgres schema and no writer in
the Worker.** Express records role assignments and invite lifecycle events through
`OrgAuditService.emit` (`backend/src/services/org-audit.service.ts:20`) into
`backend/src/repositories/org-audit.repository.ts:25`, which writes the Prisma model `OrgAuditLog`
(`backend/prisma/schema.prisma:354`). That model carries `@@map("org_audit_log")` at `:376`.

`grep -rn "org_audit" database/migrations/` returns **nothing**. The authoritative Postgres baseline
creates `audit_log` (`0000_baseline.up.sql:205`) — `organization_id`, `user_id`,
`inventory_item_id`, `action`, `change_description` — which is a different table for inventory
events, with none of `event_type`, `actor_user_id`, `target_user_id`, `old_role`, `new_role`,
`invite_id`, or `ip_address`. A search of `workers/` and `shared/` for `org_audit_log` also returns
nothing.

So this is a **schema gap, not a porting gap**: there is nowhere for a Worker implementation to
write, and adding one requires a migration before any handler change.

Sized honestly, because four of the five event types are already dormant. `AUDIT_EVENT_TYPES.ROLE_ASSIGNED`
is emitted from `org-bootstrap.service.ts:152` and is **live**. The other four —
`INVITE_CREATED`, `INVITE_REVOKED`, `INVITE_RESENT`, `INVITE_ACCEPTED`
(`organization-invite.service.ts:102/150/184/270`) — are reachable only when
`ENABLE_CUSTOM_ORG_INVITES` is set, and `backend/src/index.ts:57-59` requires the router
conditionally on that flag, which is why `contract/organization-invites-clerk-only.test.ts` asserts
404 today. The live loss at deletion is therefore **one event type — the record of who was granted
admin, and by what path**. That is also the one with the clearest compliance argument.

**The Express test for it cannot fail.** `:70-91` wraps its only assertion in `if (auditLog) { … }
else { console.warn(…) }`, with an in-file comment explaining that the audit write happens on a
separate client and may be swallowed by SQLite's interactive transaction lock. So the file that
records this behaviour proves it on Postgres and asserts nothing on SQLite — which is how a gap this
size stayed invisible. It is a Finding 1 variant with a different mechanism: not a tautology, but a
conditional that degrades to a no-op on the backend the suite actually runs against.

**A pre-existing race in both implementations, recorded as a property rather than a defect.** The
`isFirstAdmin` decision is check-then-act in both systems. The Worker reads
`SELECT id FROM users WHERE organization_id = … AND role = 'admin' AND deleted_at IS NULL`
(`bootstrap-handler.ts:302-309`) and then assigns based on the result. Express does the same before
its transaction, and its `$transaction` (`org-bootstrap.service.ts:116`) wraps only the user
*creation* at step 5, not the admin check that precedes it. Two users bootstrapping one brand-new
organization concurrently can therefore both be assigned `admin`, in either system. The unique
indexes that back the idempotency rows below — `users_clerk_user_id_key` and
`organizations_clerk_organization_id_key` (`0000_baseline.up.sql:400`, `:313`) — do not constrain
"at most one admin per organization". Consequence is bounded (an extra admin inside the caller's own
organization; no cross-tenant reach) and it is not a regression, so it is recorded here as a property
for Phase 3.2 rather than raised as a defect against the Worker.

transaction — which is an argument for a Node-side operator tool with a direct (unpooled) connection
rather than anything Worker-shaped. That constraint is the same one recorded for the runtime-role

### services/subscription.service.test.ts

Thirty-one tests, 832 lines — the largest file in Part 4 and the one with the least Worker behind
it. It drives `SubscriptionService` against a mocked Prisma client and a mocked Stripe SDK, covering
the whole billing lifecycle: create, update, cancel, trial creation, trial conversion, expiry
downgrade, reactivation, Stripe-to-local state sync, tier limits, access gating, and reminder
selection.

**The Worker has two subscription routes and no billing.** `GET /api/subscription/current`
(`handleGetCurrentSubscription`, index-minimal.ts:3039) and `GET /api/subscription/trial-status`
(`:3355`) both do a single `SELECT` against `subscription_tiers` and shape the response. That is the
entire surface. A search across `workers/src` for `stripe` outside tests returns the CSP allowlist in
`middleware/security-headers.middleware.ts:82-84` and a `stripeSubscriptionId` column read in
`utils/auth.ts:59/143/170` — no SDK, no API call, no key, no handler. Nothing in the Worker creates,
updates, cancels, converts, reactivates, or syncs a subscription.

Task 3.8 already covers adding a **Stripe webhook handler**. It does not cover the interactive
lifecycle above, and this file is the inventory of what that means.

**Finding 9 — the Worker has no scheduled-job capability at all.** Two of the behaviours here
(`downgradeExpiredTrials`, `findTrialsNeedingReminders`) are scheduled work, and there is currently
nowhere for them to run. Verified, not assumed:

- `workers/src/index-minimal.ts:274` exports `Sentry.withSentry(…, { fetch, queue })`. A search for
  `async scheduled` or a `scheduled(` handler in that file returns **zero** matches; the only
  non-`fetch` entry point is `queue` at `:467`.
- `workers/wrangler.toml` contains no `[triggers]` section and no `crons` key.

So every job in the backend's `SchedulerService` — not just these two — has no home in the Worker
today. That is precisely task 2.3's subject and it is recorded here because it arrived early, through
this file, and because it changes the reading of two rows below: they are blocked on a *runtime
capability* the Worker does not yet have, which is a different kind of blocker from a missing handler.

**A real behavioural difference in access gating, worth stating before the rows.** Express's
`isAccessActive` consults the Stripe subscription and grants access after cancellation **until the
paid period ends** (`:745`, `:771`). The Worker's `validateOrganizationStatus`
(`utils/auth.ts:187-208`) rejects on `status === CANCELED` immediately, with no period-end grace, and
its comment at `:206` records that `past_due` is deliberately allowed "for MVP phase". The Worker is
therefore **stricter on cancellation** and **looser on non-payment** than Express. Both are
defensible; neither is written down as a decision, and a customer who cancels mid-month loses access
they have paid for.

Five files in this group — `prisma-services`, `service-provider`, `storage-factory`,

implementation a factory picks, whether a container returns a singleton, whether a service was
constructed with the client it was handed. Fifty of their fifty rows describe machinery that Phase 4
deletes outright.

The Worker has no equivalent layer and does not want one. It has no DI container — handlers take
`db` and `env` as parameters and import directly. It has no storage factory — R2 arrives as a
binding (`env.CSV_UPLOADS`), chosen by `wrangler.toml` rather than by `NODE_ENV` at runtime. It has
no database factory — `neon(getConnectionString(env))` is the only path. So "does the factory pick
the right implementation for this environment?" is a question the Worker cannot ask, because the
answer is decided at deploy time by configuration rather than at runtime by code.

That makes these files cheap to dispose of, but it is worth being explicit about what is *not*
being retired with them. Two properties inside this group are real and tenant-relevant, and they are
called out in their rows rather than swept along: organization context reaching the query
(`service-provider.test.ts:191`) and provider instances not being shared across organizations
(`:128`). Both are already covered in the Worker by the tenant-isolation suites from #462, and both
would otherwise look like collateral damage in a wiring-file cull.

### integration/auth-tier-override.test.ts

Three tests, real Prisma, real `authenticateToken` middleware mounted on a throwaway Express app
with one route that returns 403 unless `req.tierLevel === 'premium'` (`:26-31`). Small file, and the
first two carry one of the more important properties in the whole audit.

**The property: a tier claim inside a JWT must not be believed.** `:16` signs a token asserting
`tierLevel: 'premium'` for an organization the database records as `starter`, and asserts the request
is refused 403. `:55` is the mirror — the database is updated to `premium`, the cache is invalidated,
a *stale* token still says `starter`, and access is granted. Taken together they establish that the
database is authoritative for entitlement and the token is not, in both directions. That is a
privilege-escalation guard, and it is the only place in Part 4 where one is tested directly.

**The Worker gets this right, by construction — with one trap worth recording.** Checked rather than
assumed: `workers/src/utils/auth.ts:29` declares an optional `tierLevel` claim on `TokenPayload`, so
the type says a token may carry one. **Nothing reads it.** All three uses of `.tierLevel` in that
file (`:158`, `:166`, `:281`) come from the row returned by the `subscription_tiers` query, never
from the payload. So the escalation this test defends against cannot happen in the Worker.

The trap is the declared-but-unread claim itself. A future reader who needs a tier in a handler will
find `payload.tierLevel` offered by the type and may reach for it, at which point the guard is gone
with no test to notice. The field should be deleted from `TokenPayload` rather than left as an
attractive nuisance.

**A related difference with no security consequence, recorded so it is not mistaken for one.** Express
caches subscription state in a module-level `Map` (`auth.middleware.ts:73`) with a TTL, exports
`invalidateSubscriptionCache` (`:64`) so webhooks can apply tier changes immediately, and stamps an
`X-Org-Tier-Version` header (`:39`) on every response. The Worker has **no cache** — the comment at
`utils/auth.ts:8` says "Query and cache subscription tier from Neon", but there is no `Map` and no
cache in the file; it queries `subscription_tiers` on every authenticated request. That is stricter,
not weaker: staleness is impossible, so the invalidation hook and the version header have nothing to
do. Confirmed that nothing depends on the header — a search across `frontend/src` for
`tier-version`/`tierVersion` returns nothing, so it is set by Express and read by no one. The cost is
one extra query per request, which is a performance question rather than a correctness one, and the
misleading comment should be corrected.

### integration/multi-tenant-subscription-transitions.test.ts

Twelve tests, real Prisma, driving `SubscriptionService.updateSubscription` for upgrades and
downgrades. The genuine property running through the file is a good one and easy to lose sight of
among the misnamed tests: **a tier change must never destroy data or reset usage counters.** Four
tests assert exactly that — products survive, `totalSkus` and `storageUsedBytes` are preserved
across both directions, even when usage is far over the new limit (`:816` keeps 1800 products
against a 500 cap).

**A defect in Express, found by reading two rows against each other.** `:653` is named
`should sync orgUsage limits with tier limits on upgrade`. It calls
`updateSubscription(orgId, 'professional')` — and then **performs the sync itself**:

```
backend/src/tests/integration/multi-tenant-subscription-transitions.test.ts:~680
  await prisma.organizationUsage.update({ … maxSkus: TIER_LIMITS.professional.max_skus … });
  …
  expect(usage?.maxSkus).toBe(50000);
```

It asserts the value it just wrote. `:120` does the same upgrade **without** the manual fix-up and
finds `maxSkus` still `500` and `maxUsers` still `1` (`:178-179`) — the pre-upgrade values. So
`updateSubscription` does **not** propagate tier limits into `organizationUsage`, and the test named
for that property masks it by doing the work itself.

That is a fifth variant of the pattern: not an assertion that cannot fail (Finding 1), not one that
codifies the opposite of its name (the concurrency file), not one that tests something other than
its name (route filtering) — but a test that **performs the behaviour it claims to verify**. `:120`
is the honest record of what the code does; `:653` is the wishful one, and they contradict each
other in the same file.

**Why this matters for #471 rather than for Express.** Express is being deleted, so the defect is
mostly of historical interest — except that #471 asks the Worker to implement usage limits, and the
obvious move is to copy Express's model of storing `max_*` values on an `organization_usage` row.
That model is exactly what produces this bug: limits live in two places and something has to keep
them in step.

The Worker currently has **both models at once**, which is worth resolving deliberately:

- `getOrganizationLaunchTier` reads `tier_level` from `subscription_tiers` and derives limits from
  `LAUNCH_TIER_LIMITS` (`index-minimal.ts:3980`) **at call time**. Nothing can go stale.
- The `POST /api/users` gate (`index-minimal.ts:2673`) reads `ou.max_users` from the stored
  `organization_usage` row instead — the seeded literal `1` from `:3084`.

So the Worker's one live gate consults the stale-by-design copy while its bulk-import path consults
the derived one. #471 should pick the derived model and drop the stored `max_*` columns from the
read path, which removes this entire class of bug rather than porting it.
