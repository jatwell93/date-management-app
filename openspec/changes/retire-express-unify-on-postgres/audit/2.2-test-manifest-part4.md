#### Finding 3 — a cross-tenant leak on the *write* path, found by auditing the two rows above (#466)

Added after Findings 1 and 2, when the two `worker-shaped-rewrite` rows for cross-tenant
UPDATE/DELETE were worked. Those rows predicted a mutation keyed on id alone; the mutations turned
out to be correctly scoped. The defect was one layer over:

`updateInventoryItem` validated that a supplied `locationId` belonged to the caller's organization
but did **not** validate `productId` — while `createInventoryItem` validated **both**. Meanwhile 20
JOINs across `database.ts` resolved `products`, `store_areas` and `inventory_items` by id alone,
without correlating on organization (`JOIN products p ON ii.product_id = p.id`). The two compose:

```
PATCH /api/inventory-items/{own_id}   {"productId": <victim's product id>}   -> 200 OK
GET   /api/reports/loss-by-sku                                               -> victim's sku, name, cost_price
```

Product ids are `SERIAL`, so the victim id is enumerable. Confirmed by real-SQL test, not by
inspection: the update returned the item with the foreign `productId`, and `getLossBySkuReport`
for the attacker's organization then returned `SKU-SECRET` — a row belonging to another tenant.

Fixed on both sides, because either alone leaves a hole: the missing `productId` check (which stops
the bad reference being created) and all 20 uncorrelated JOINs (which stop any pre-existing or
future bad reference being resolved). Verified by mutation — removing the `productId` check fails
exactly one test, removing the JOIN correlation fails exactly two.

**Why this matters for the manifest method.** A `worker-shaped-rewrite` row is a claim that a
property is untested, and the natural way to close one is to write the test and move on. Here,
writing the test is what surfaced a live vulnerability that no Express row described — the Express
suite has no equivalent, because Prisma's service-scoped constructor makes the reference-repointing
shape hard to express. Rows should be worked by exercising the Worker against real SQL, not by
reading the Worker and judging it equivalent.

**One deliberate exception, recorded so it is not "fixed".** `reviewCatalogueCorrection` is the
only mutation in `database.ts` with no organization predicate, and it is correct: catalogue
corrections are reviewed by a **platform** admin across all tenants, gated by `isPlatformAdminUser`
rather than tenant membership. A sweep for "mutations missing `organization_id`" flags it first and
the guard that justifies it lives in another file, so the reasoning is now a comment at the method.

#### Finding 4 — the Worker enforces no usage limit on any interactive path

Established while working the `concurrency` and `feature-limits` files. Unlike Findings 1–3 this is
**not fixed** — it is a parity gap for Phase 3.1 to close, recorded here because it governs every
`feature-limits` and `concurrency` row below and would otherwise be rediscovered three times.

Three independent facts, each enumerable rather than judged:

1. **`workers/src/utils/feature-gates.ts` has no production importer.** A repo-wide search for the
   module path across `workers/src/**` outside `*.test.ts` returns **nothing**. Its five exports
   (`checkFeatureAccess`, `checkUsageLimit`, `requireFeatureAccess`, `enforceUsageLimit`,
   `formatUsageLimitCTA`) are referenced only by `utils/feature-gates.test.ts`,
   `__tests__/feature-gates-integration.test.ts`, and `__tests__/usage-limits-integration.test.ts`.
   The module is dead code carrying a 362-line test suite.

2. **Its SQL cannot run against the schema.** `checkUsageLimit` queries `"Product"`, `"User"`,
   `"InventoryItem"` and `"Upload"` — quoted PascalCase Prisma table names — while the Postgres
   schema uses `products`, `users`, `inventory_items`, `uploads`. Exercised against pglite, every
   branch throws and falls into the catch:

   ```
   [FeatureGate] Error checking usage limit: error: relation "Product" does not exist
   PROBE max_skus => {"isWithinLimit":false,"currentUsage":0,"limit":5000,"error":"Failed to check max_skus limit"}
   [FeatureGate] Error checking usage limit: error: relation "User" does not exist
   [FeatureGate] Error checking usage limit: error: relation "Upload" does not exist
   ```

   The module fails closed, so wiring it up as-is would reject every create. Its own test suite
   passes because it supplies a mock `dbClient` returning canned rows, which never validates SQL —
   the same class of defect as Finding 1, one layer down: a test that exercises a query string
   nothing will ever execute.

3. **The one inline gate reads a counter nothing maintains.** `POST /api/users`
   (`index-minimal.ts:2673`) does check `max_users`, against `organization_usage`. But
   `organization_usage` is written in exactly one place in the entire Worker — a lazy
   `INSERT ... ON CONFLICT DO NOTHING` of literal zeros inside `handleGetOrganizationUsage`
   (`index-minimal.ts:3084`), seeding `active_users` 0, `max_users` 1, `total_skus` 0. There is no
   `UPDATE organization_usage` anywhere, and no database trigger (no `CREATE TRIGGER` exists in any
   migration). So `active_users` is permanently `0`, the guard `activeUsers >= maxUsers` evaluates
   `0 >= 1` → false, and the limit **never fires**. The same staleness makes
   `GET /api/organization/usage` report `total_skus: 0` for every organization regardless of
   catalogue size.

`POST /api/products` (`handleCreateProduct`, `index-minimal.ts:2266`) performs no limit check at
all. The **only** working usage enforcement in the Worker is on the bulk catalogue-import path,
where `isCatalogueWithinLimit` (`upload/catalogue-import.ts:114`) compares a projected SKU count
against the `max_skus_snapshot` captured at job creation from `LAUNCH_TIER_LIMITS`
(`index-minimal.ts:3980`) — a separate mechanism that does not consult `organization_usage` and
does not cover interactive creates.

None of this is a tenant-isolation defect: no organization can reach another's data through it.
It is a revenue-and-capacity gap, and it means **no `feature-limits` row below may be resolved
`worker-equivalent-exists` on the strength of `feature-gates.ts`.**

### integration/multi-tenant-penetration.test.ts

The backend's `penetration` gate: 20 supertest-driven attack simulations against the real Express
app with a real Prisma client, in three groups — injection/IDOR/mass-assignment (9), JWT
validation (6), and route-parameter tampering (5).

**Read the assertions before trusting the file name.** Several tests in the first group send **no
`Authorization` header at all**, so the 403 they assert is the unauthenticated-request path and
the tampering they are named for is never exercised (`:248`, `:321`, `:395`). Others assert a
disjunction satisfied either way — `:196` and `:274` accept *any* status >= 400 *or* an empty
200 body, and `:457` accepts `[200, 403, 500]`, so a 500 passes a test named "should accept valid
JWT". These are recorded per row; where a test does not constrain the behaviour it names, that is
stated rather than carried forward as coverage.

**The Worker's structural position matters for every `org_id`-tampering row.** In
`workers/src/index-minimal.ts` there is exactly **one** assignment of an organization identifier —
`const organizationId = auth.organizationId` at `index-minimal.ts:3352`, taken from the verified
JWT. No route parameter, query string, or request body is ever read into it. The attack surface
these tests probe is therefore *absent by construction* in the Worker, not merely untested — the
same positive-evidence standard applied to the Clerk-managed invite rows in Part 2, rather than
the weaker "no Worker analogue found" argument.

### integration/multi-tenant-concurrency-load.test.ts

Nominally the backend's `concurrency` gate: six tests firing 10–100 simultaneous writes at an
organization sitting on a tier boundary, to prove limits hold under races.

**None of the six exercises application code.** Every operation is a direct `prisma.product.create`,
`prisma.user.create`, or `prisma.organizationUsage.update` issued by the test body itself. No
service, no controller, no route, no feature-gate middleware is on the path. The file's own comments
say so at `:110`, `:185`, `:436` and `:523` — *"Direct Prisma writes bypass feature-gate
enforcement"* — and the assertions were then written to match that reality rather than the test
names.

The result is a variant of Finding 1 worth naming separately, because it is not tautological and so
does not show up in a `expect(true).toBe(true)` sweep. These tests are **inverted**: the assertion
codifies the very outcome the name promises to prevent. `should prevent SKU overshoot under extreme
concurrent load` seeds 490 SKUs against a 500 cap, fires 100 concurrent creates, and asserts
`expect(finalCount).toBe(590)`. The test passes *because* the limit was exceeded, and would fail if
enforcement were ever added. It is not a gate; it is a regression test against having one.

Consequently **no row here can be retired "in favour of" Worker coverage, and none can be carried
forward as a preserved gate** — there is no gate to preserve. What must survive into Phase 3.2 is
the *property* each test is named for, none of which this file establishes and, per Finding 4, none
of which the Worker currently enforces either. Each row below therefore records the Express test as
`retire` (it constrains nothing) while naming the property in the Evidence cell so 3.2 has the list.
