# Task 2.3 — Action-level schedule matrix

**Change:** `retire-express-unify-on-postgres`
**Status:** PROPOSED — every `Target` cell is a proposal. Deletion and rehoming authority is human.

## Scope and method

The task asks for an **action-level** matrix built from "actual `SchedulerService` registrations and
dormant job exports — not a six-file list". So the unit here is a *scheduled action*, not a file: a
job that performs four distinct operations under one cron expression yields four rows, because each
one rehomes, retries, and fails independently.

Three things were established by tracing rather than assumed, and each changed the shape of the
matrix:

1. **Registration was traced by importer, not by filename.** `backend/src/jobs/` holds six files.
   Only four are imported by `scheduler.service.ts` (`:6-9`). `daily-metrics.job.ts` and
   `daily-report-email.job.ts` have **no production importer at all** — the former is reachable only
   from two unit tests, the latter from nothing whatsoever.
2. **Every `cron.schedule` call site was read for a timezone argument.** None passes one.
3. **The Worker's scheduled capability was re-verified fresh** rather than carried from Finding 9,
   and the finding needs refining — see Finding 9-R below.

Recurrence that does not go through `SchedulerService` is included as its own class. Three services
run `setInterval` loops that are, functionally, scheduled work with a rehoming problem; omitting them
would leave a gap in the Phase 4 deletion authority that 2.5 depends on.

**Column meanings.** `Status` is active / dormant / interval / manual. `Cron (declared → actual)`
records the schedule the code comments claim against the expression actually passed, because those
disagree in one case. `Overlap prevention` and `Idempotency` are recorded as observed, not as
intended.

## Findings

### Finding 9-R (refines Finding 9) — Queues exist; only Cron Triggers are missing

Finding 9 recorded that "the Worker has no scheduled-job capability at all". Re-verifying against the
current tree sharpens that, and the correction matters for sequencing:

- **Confirmed still true:** a search for `scheduled` in `workers/src/index-minimal.ts` returns **zero**
  matches, and `workers/wrangler.toml` declares no `[triggers]` section and no `crons` key. There is
  no `scheduled` export and nothing to invoke one.
- **But Queues are already configured**, in both environments: `wrangler.toml:49` and `:115` declare
  producers, `:53` and `:119` declare consumers, with `max_retries = 5`, `retry_delay = 30`,
  `max_concurrency = 1`, and a `dead_letter_queue`.

So the two rehoming targets are not equally distant. Every row this matrix proposes for a **Queue**
(rows 5, 7, 14) targets infrastructure that **exists today and already has a retry and DLQ policy** —
which is more than any current job has. Every row proposed for a **Cron Trigger** is blocked on
adding both a `[triggers]` block and a `scheduled` export.

That suggests a cheaper sequencing than 3.3 currently implies: the per-recipient email sends can move
to the existing Queue independently of, and before, any Cron Trigger work.

### Finding 11 — The markdown job reads SQLite directly, bypassing Prisma

`SchedulerService.updateAllInventoryMarkdownStatuses` calls `getDb()` and issues
`db.prepare('SELECT id FROM organizations').all()` (`scheduler.service.ts:81`) and
`db.prepare('SELECT id, expiry_date FROM inventory_items WHERE organization_id = ?')` (`:97`). This is
raw `better-sqlite3`, not Prisma.

It matters for two reasons. First, most of the retirement work assumes the path from Express is
Prisma-to-Postgres; this action has no Prisma layer to swap out and must be rewritten against Neon
rather than ported. Second, it is a **synchronous** driver call — the shape does not survive contact
with a Worker regardless of the SQL dialect.

Rows 1, 2, and 26 all inherit this. Row 26 is the one to watch, because it reaches the same SQLite
read through an HTTP route, so it will surface in 2.1's route matrix as a live endpoint whose
implementation dies at Phase 4.

### Finding 12 — The scheduled backup backs up a file that will not exist

`DatabaseBackupService.createBackup` writes `backup-${timestamp}.sqlite`
(`database.backup.service.ts:44`) by file-copying the SQLite database. Post-cutover there is no such
file, so this is not a rehoming candidate at any priority — it is a capability that must be
**reimplemented from nothing**, and row 3 is recorded as retire-with-the-backend accordingly.

This is direct input to task 2.4, which asks for the backup capability's home and already carries the
measured constraint that Neon free-tier PITR reaches **6 hours** with **one** manual snapshot. Worth
stating plainly for that decision: the current scheduled backup provides 30 days of retention across
10 files. Choosing "Neon-native backups" alone is therefore not a like-for-like replacement of what
exists today — it is a reduction from 30 days to 6 hours. The scheduled-R2-export option is the one
that preserves the current posture.

### Finding 13 — Three-way schedule disagreement in the dunning job, and a 02:00 collision

`dunning.job.ts` states its schedule three times and they do not agree:

- File header (`:10`): "Schedule: Daily at 01:00 UTC (0 1 * * *)"
- Inline comment (`:27`): "Daily at 02:00 UTC (1 hour after database backup at 01:00 UTC)"
- Actual expression (`:28`): `cron.schedule('0 2 * * *', ...)`

`scheduler.service.ts:65` repeats the first version: "Initialize dunning job (runs daily at 01:00
UTC)". The code runs at 02:00; two of the four statements say 01:00.

The consequence is not cosmetic. **Row 1 (markdown recalculation) is also `0 2 * * *`**
(`scheduler.service.ts:49`). The comment at `dunning.job.ts:27` reasons explicitly about avoiding a
collision with the 01:00 backup, and in doing so places dunning exactly on top of the markdown job —
the heaviest action in the set, which iterates every inventory item of every organization.

No test catches this. `tests/unit/scheduler.service.test.ts:89-90` pins both inline expressions
(`'0 2 * * *'` and `'0 1 * * *'`) but mocks `startDunningJob` (`:42`), so dunning's real expression is
never observed alongside them. This is the class of gap the 2.2 audit kept finding: the assertion is
real, but the thing that would have made it fail is mocked out.

Rehoming is the natural moment to fix it, since Cron Triggers make each schedule explicit in
`wrangler.toml` where a collision is visible in one place.

### Finding 14 — The only job lock in the codebase cannot acquire, and reports it as contention

`JobLockRepository.acquire` (`repositories/job-lock.repository.ts:17`) implements distributed locking
as:

```
INSERT INTO migrations (name, appliedAt) VALUES (${lockKey}, ${expiresAt})
```

and `release` (`:44`) as `DELETE FROM migrations WHERE name = ${lockKey}`. Lock keys are of the form
`daily-metrics-2026-08-27` (`daily-metrics.job.ts:38`).

**It does not collide with the Phase 1 migration ledger** — this was checked before writing, because
it was the obvious worry. The Phase 1 runner owns `schema_migrations`
(`src/database/migrations/runner.ts:404`), a different table, and `catalog-comparison.ts:257`
explicitly classes the legacy `migrations` table as migration-only and filters it out of catalog
comparison. So the lock writes to a legacy Prisma table that Phase 4 removes with Prisma. No hazard
to the adoption ledger.

What is actually wrong is narrower and more certain:

1. **The `INSERT` names a column that does not exist.** The statement is
   `INSERT INTO migrations (name, appliedAt)`. The Prisma model declares
   `appliedAt DateTime @map("applied_at")` (`backend/prisma/schema.prisma:678`), and the Postgres
   baseline creates the column as `"applied_at"` (`database/migrations/0000_baseline.up.sql:278`).
   There is no `appliedAt` column in either backend — this is a Prisma *field* name used in raw SQL.
   The insert therefore always throws.
2. **The failure is swallowed as "lock already held".** `acquire` catches everything, checks for
   `errorCode === 'SQLITE_CONSTRAINT'` (`:28`), does not match a missing-column error, and falls
   through to `return false` (`:39`). `DailyMetricsJob.execute` reads that as contention and logs
   *"Daily metrics job is already running, skipping"* (`daily-metrics.job.ts:47`) before returning.
   So the job would silently no-op on every single run while reporting a plausible reason.
3. **The lock is also SQLite-coupled even once (1) is fixed.** Postgres raises `23505` for a unique
   violation, not `SQLITE_CONSTRAINT`, so on Neon the expired-lock recovery branch never runs and a
   crash between acquire and release would lock the job out permanently. The unique index the
   mechanism depends on does exist (`0000_baseline.up.sql:502`), so this is the only remaining
   blocker after the column name.
4. **It is reachable only from dormant code.** `JobLockRepository` is registered in DI
   (`di/container.ts:62`) and imported by exactly one job — `daily-metrics.job.ts`, which nothing
   registers. So **no live scheduled action in this codebase has overlap prevention**, including row
   15, which deletes files.

No test catches (1) or (2): `tests/unit/job-lock.repository.test.ts:12-15` injects a mock exposing
`$executeRaw` and `$queryRaw` as `vi.fn()`, so the SQL string is never executed and never inspected —
`:23` asserts only `toHaveBeenCalledTimes(1)`. The same shape as Finding 13: a real assertion, with
the thing that would fail mocked away.

Point 1 is the same defect class as issue #471 — Prisma-style identifiers in raw SQL against a
snake_case schema. Recorded here rather than filed separately because the action is dormant and dies
at Phase 4 either way; if the job is revived ahead of the cutover it should be filed then.

The forward-looking half: whatever rehomes row 15 needs overlap prevention, and the answer on Neon is
a conditional single-statement insert or an advisory lock, not this.

### Finding 15 — No schedule declares a timezone; every comment claims UTC

`cron.schedule(expression, handler)` is called six times in production code — `scheduler.service.ts:49`
and `:56`, `trialExpiration.job.ts:27`, `dunning.job.ts:28`, `stripe-sync.job.ts:207`,
`credit-claim.job.ts:109` and `:115`. **None passes an options object**, so all of them run in the
Node process's local time.

Meanwhile the comments assert UTC at `trialExpiration.job.ts:9` and `:26`, `dunning.job.ts:10` and
`:27`, and `scheduler.service.ts:61` and `:65`. The only `timezone: 'UTC'` values that appear anywhere
are in `getJobConfig()` returns on the two **dormant** jobs (`daily-metrics.job.ts:146` and `:268`,
`daily-report-email.job.ts:104`) — objects that no caller reads.

Today this is probably harmless: a container with `TZ` unset runs UTC, so the schedules likely land
where the comments claim. But it is unasserted anywhere, and it is the kind of thing that silently
shifts by an hour when a host's timezone or DST changes. Trial expiry and the 7-day dunning grace
period are both date-boundary computations, so an off-by-one-day is the failure mode, not an
off-by-an-hour.

Cloudflare Cron Triggers are **always UTC** and take no timezone parameter, so rehoming resolves this
by construction. Recorded because it changes what "same schedule" means during the move: the migration
should assert UTC was always the intent, and rows 4 and 8 should be checked for date-boundary
sensitivity before their expressions are copied across verbatim.

### Finding 16 — Two of the six job files are dormant, and one of them says it is enabled

`daily-metrics.job.ts` (both classes) and `daily-report-email.job.ts` are exported, documented, and
unregistered. `daily-report-email.job.ts` has no importer at all — not even a test.

The trap for anyone auditing at file level: `daily-metrics.job.ts:147` and
`daily-report-email.job.ts:105` both return `enabled: true` from `getJobConfig()`. Nothing calls
`getJobConfig()`. So the codebase contains a configuration object that asserts these jobs are enabled,
sitting beside no registration that would enable them.

The substantive loss is row 21. The hourly webhook check is not reporting — it contains a
replay-attack detector that alerts when `processed_webhook_events` grows more than 5x hour-on-hour
(`daily-metrics.job.ts:217-220`), plus a daily webhook-error-count alarm. These are security controls,
written and commented as delivered work ("NEW — 16A.B.7"), that have never run. Rehoming decisions for
rows 19-21 should be made on that basis rather than as telemetry cleanup. **Filed as #477**, because the
gap is independent of this migration: the monitoring is absent from both backends, so it survives
Phase 4 rather than dying with Express.

## Handover notes

- **Sequencing.** Row 4 is the priority: until `downgradeExpiredTrials` has a home, expired trials
  keep their entitlements. That is the mirror of issue #471 already recorded at task 3.1.i.
- **Cheapest first move.** Rows 5, 7, and 14 can move to the existing Queue without any Cron Trigger
  work, and would gain the retry and DLQ policy they currently lack (Finding 9-R).
- **The disabling switch is test-only.** `DISABLE_SCHEDULER_JOBS` (`scheduler.service.ts:42`) is set
  in exactly one place, `tests/setup-neon-env.ts:6`. There is no production kill switch for the
  scheduler, and 3.3 should not assume one exists when staging the cutover.
- **Two findings are worth resolving before the move, not during it:** Finding 13 (the 02:00
  collision) and Finding 14 point 3 (lock rows in the migrations ledger).
