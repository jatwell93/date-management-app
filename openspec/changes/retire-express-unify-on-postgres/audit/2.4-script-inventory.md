# Task 2.4 — Operational script inventory (`backend/scripts/`)

**Change:** `retire-express-unify-on-postgres`
**Status:** PROPOSED — every `Decision` cell is a proposal. Deletion authority is human.

## Scope and method

`backend/scripts/` holds **30 tracked files**. The task text names about fourteen of them, so the
first job was enumerating the directory rather than working the list. The omissions are not trivia:
the largest single omission is a **seven-script migration cluster** (`migrate.js`,
`migrate-production.ts`, `migrate-production-simple.js`, `migrate-production-doppler.js`,
`migrate-upload-status.ts`, `list-migrations.ts`, `verify-migration.js`), which is exactly the group
Phase 1 was built to replace.

**This inventory does not decide from scratch.** Two earlier passes already recorded dispositions,
and 2.4's real job is to discharge their conditions:

1. **`design.md:188-221`** carries 16 script rows, every one reading *"**Replace / do not delete**
   until ⟨condition⟩"*. Its stated search boundary (`design.md:223-226`) scopes it to
   migration-touching scripts and defers "seeds, export/import, backup, and diagnostics" to this
   task. So the 16/14 split between that table and this one is intended, not an oversight.
2. **`tasks.md` correction (a)** pre-decided both seeders as superseded.

So each row below records the **prior disposition**, then whether Phase 1 actually discharged its
condition. Where it did not, the row says so rather than quietly promoting the script to retirable —
that distinction is the whole value of the exercise, and two rows turn on it.

**How supersession was established.** Not by inference: the Phase 1 runner names the scripts it
replaces, in source. `preflight.ts:5-6` names `verify-neon*.ts`, `test-connection.ts`,
`test-write-permissions.ts` and `check-tables.ts`; `status.ts:7-8` names `list-migrations.ts` and the
`migrate:status` command; `verify.ts:4-5` names `verify-migration.js` and `migrate-production.ts`;
`seed.ts:4` names `seed-tier-flags.js`. Ten scripts are retirable on that evidence alone.

**Data path** records what each script actually talks to, because it is the single best predictor of
whether a script survives: `SQLite`, `Prisma`, `Neon/pg`, or `none`.

## Findings

### Finding 17 — The backup capability has no owner in either backend

Task 2.4 asks where the backup capability should live. Three artefacts implement it today and **all
three are SQLite file-copies**:

- `backend/scripts/backup.sh` — copies `../src/database.sqlite` into `../backups`.
- `backend/src/services/database.backup.service.ts:38` — writes `backup-<timestamp>.sqlite`, retaining
  30 days / 10 files (`:11-15`).
- `backend/src/routes/database.backup.routes.ts` — the operator-triggered route.

Nothing here has a Postgres path, so **none of this relocates**; the capability is a reimplementation.
Two things should be settled explicitly rather than by default:

1. **What is being replaced is 30 days of restore points.** Combined with the measured Neon free-tier
   constraint already in tasks.md (b) — 6-hour PITR reach, one manual snapshot — choosing
   "Neon-native backups" alone is a **reduction**, not a like-for-like move. Only the scheduled-R2-
   export option preserves the current posture. This is also recorded as 2.3 Finding 12.
2. **The two implementations already disagree on where backups go.** `backup.sh` writes to
   `backend/backups` relative to itself; the service writes to `./backups` relative to the process
   working directory. Whichever survives, the operator-facing contract needs stating once.

The scheduled half is separately recorded as retire-with-the-backend (2.3 matrix row 3). The **route**
belongs on 2.5's rehoming checklist, per the task text.

### Finding 18 — Four historical backfills are blocked on a verification that was never run

`design.md` conditions the retirement of the tenant-ID and role backfills on adoption *verifying* the
data, not merely on the backfills having been run at some point:

- `backfill-org-ids.ts` / `check-null-org-ids.ts` / `audit-org-ids.ts` — "until adoption verifies
  production has no unresolved tenant IDs".
- `backfill-canonical-roles.js` — "until adoption verifies canonical production roles".
- `migrate-upload-status.ts` — "until Phase 2 classifies it as already executed/retirable".

That condition is **not discharged**. Phase 1's `migrate:verify` checks table existence, the catalog
fingerprint, and the 54-row `tier_feature_flags` reference set. It does not assert that
`organization_id` is non-NULL across tenant tables, that `users.role` holds only canonical values, or
that no `uploads.status = 'complete'` rows remain. The 1.9 production drill verified reference data
against restored data — not these three data invariants.

So these five scripts are *probably* retirable and cannot be shown to be. The gap is small and worth
closing directly rather than carrying five scripts to keep the option open. A single read-only query
against production answers all three:

- NULL `organization_id` counts across `products`, `inventory_items`, `store_areas`, `users` — the
  tables `check-null-org-ids.ts` already enumerates;
- distinct `users.role` values against `{admin, manager, team_member}`;
- count of `uploads` with `status = 'complete'`.

Two follow-ons worth separating:

- **The hard-coded organization identity must not survive.** `backfill-org-ids.ts:4` embeds
  `DEFAULT_ORG_ID = '248c0a81-db22-4e41-869d-61634de4a304'`. design.md already flags this. Deleting
  the script removes it; nothing should rehome it.
- **The tenant-ID *audit* is worth keeping even though the *backfill* is not.** `audit-org-ids.ts`
  checks a live multi-tenant invariant — that no row is missing its tenant scope — and that invariant
  outlives the migration. Given both cross-tenant vulnerabilities found in this audit (#462, #466),
  the check belongs in the Worker's conformance suite as a test, not in a script an operator has to
  remember to run. That is the "rehome" half of the row.

### Finding 19 — `neon-to-sqlite.ts` is the old rollback plan, and keeping it would be worse than deleting it

At 570 lines this is the largest script in the directory, and it is a genuine piece of engineering:
table-by-table export, row-count verification, optional `pg_dump` snapshot. It exists because SQLite
was the fallback if Neon went wrong.

After Phase 1 that is no longer the recovery story. Recovery is Neon PITR and branch restore — the
path 1.9 actually rehearsed, with measured constraints recorded. Exporting production data into a
SQLite file the system can no longer run does not restore service; it produces an artefact with no
consumer.

Recorded as a finding rather than a matrix cell because the risk is in *keeping* it: a working-looking
emergency export script invites use during an incident, and using it would consume time without
producing a recovery. If anything survives here it is the `pg_dump` snapshot option, which belongs
with the Finding 17 backup decision rather than as a rollback tool.

### Finding 20 — `run-tests.js` must be deleted last, not early

`backend/scripts/run-tests.js` is the backend test launcher: it assigns each invocation its own SQLite
database file in the OS temp directory *before* Vitest starts, so `globalSetup` and every worker fork
inherit the same path and concurrent runs cannot clobber each other.

It backs `npm test`, `test:diff`, `test:coverage`, `test:watch` and `test:verbose` in
`backend/package.json:11-18`, and the root `test:backend:diff` (`package.json:21`) delegates straight
to it. That is the command CLAUDE.md names as the pre-commit gate for backend changes.

Recorded because it is the one script in this directory whose removal would break the ability to
verify the removals around it. Nothing about it is worth preserving past the backend — it is SQLite
plumbing — but it is ordering-critical, and it should be entered on 2.5's checklist as
delete-with-the-backend rather than swept up as a retirable operational script.
