# Task 2.5 — Rehoming checklist (deletion authority for Phase 4)

> **This document gates all deletion in Phase 4.** Nothing may be deleted that does
> not appear here with either a target or a recorded retirement decision.
>
> Every `Decision` cell carries a mandatory `PROPOSED:` prefix. Deletion authority
> is human. This checklist proposes; Josh decides.
>
> **What this document is not.** It is not a re-derivation of tasks 2.1–2.4. Those
> four deliverables already carry 135 route rows, 1,977 test-behaviour rows, 26
> schedule rows and 30 script rows, each with its own evidence. Restating them here
> would create a second copy that drifts from the first. Sections **A–D** therefore
> **roll up** the prior deliverables by decision class and name the file that holds
> the row-level evidence. Sections **E–M** are the categories the task text names
> that **no prior task covered**, and those are enumerated at row level here for
> the first time. §M is the one partial exception: its rows were pre-recorded as
> keeps by Phase 1, and this document collects them rather than deciding them.

**Method for the new sections.** Enumerate from the filesystem (`git ls-files`),
not from memory or from the task wording — 2.3 and 2.4 both found the task text
undercounted. For each row, establish the **live** Worker counterpart by tracing
importers, not by matching filenames. That distinction did real work here: nine
`workers/src/middleware/*` modules have names that look like exact counterparts to
the Express middleware and are reachable only from an abandoned entry point
(Finding 22).

**Live Worker entry point.** `workers/build.js:11` bundles
`workers/src/index-minimal.ts` to `dist/index.js`, which is what `workers/wrangler.toml:2`
deploys. Any module not reachable from `index-minimal.ts` is not in production,
whatever its filename suggests.

### Finding 21 — One frontend call site does not follow the API base, and a test pins it that way

`frontend/src/components/StorageQuotaWarning.tsx:61` fetches a **relative** URL:

```ts
const response = await fetch(`/api/storage-quota/${userId}?tier=${subscriptionTier}`, {
  headers: { Authorization: `Bearer ${authToken}` },
});
```

Every other API call site in the frontend goes through `buildApiUrl`
(`lib/api.service.ts:42`), which prefixes `API_BASE_URL`. This one does not, and
the file does not import `buildApiUrl` at all.

There is nothing to rewrite the relative URL: the frontend is Vite, so there is no
CRA `proxy` field; `frontend/package.json` declares none; and there is no
`frontend/public/_redirects` for Pages. The request therefore goes to the origin
serving the app — Cloudflare Pages — which does not serve `/api/storage-quota`.

The failure is silent. The `catch` at `:88-91` sets an error string into component
state, and the component renders nothing when it has no quota. A storage-quota
warning that never appears looks identical to a user who is under quota.

**The test asserts the broken URL as correct.**
`frontend/src/components/__tests__/StorageQuotaWarning.test.tsx:54-55`:

```ts
expect(fetchMock).toHaveBeenCalledWith('/api/storage-quota/1?tier=free', expect.anything());
```

This is the same pattern the 2.2 audit named repeatedly — a real assertion with the
thing that would fail mocked away. `fetchMock` answers any URL, so the one property
that matters in production (does this URL reach the API?) is exactly the property
the mock removes.

**Why this belongs on the rehoming checklist rather than in an issue.** The
`/api/storage-quota` route is Express-only; the live Worker has no such route
(`grep -n "storage-quota" workers/src/index-minimal.ts` returns one comment at
`:3991` and no route). So Phase 3.1 must build the Worker route regardless, and
this call site must be corrected as part of the same work. It does not survive
Phase 4 independently, which is the discriminator established at #460.

**Proposed:** fix the call site to use `buildApiUrl`, and change the test to assert
against the built URL rather than the literal path — otherwise the corrected code
fails the test that documents the defect.

### Finding 25 — The offline queue blocks on its first failure — but nothing populates it

> **Corrected 2026-08-28.** As first written, this finding claimed the cutover would
> jam users' offline queues. That is **wrong**, and the correction is recorded here
> rather than by rewriting the finding, because the mistake is instructive.
>
> `addOperation` (`offline-sync.ts:149`) has **no production caller**. All 25 call
> sites are test files (`lib/__tests__/offline-sync.test.ts`,
> `lib/__tests__/offline-sync-strategy.test.tsx`, `tests/offline-sync.test.ts`). The
> queue is therefore always empty in production, `processQueueOperations` never
> iterates anything, and the jam described below **cannot occur today**.
>
> The service is *partially* wired, which is why it read as live:
> `ClerkAuthProvider.tsx:101` gives it an auth token provider,
> `HandheldContext.tsx:55` sets its sync strategy, and `useSyncStatus.ts:16,19`
> renders `getPendingOperationCount()` — which returns the queue length (`:413-415`)
> and is therefore structurally always `0`. **The handheld UI shows a pending-
> operations counter that can never be non-zero.**
>
> The offline path that *does* work is a different module: `lib/sync-manager.ts`
> with `lib/offline-storage.ts`, handling `pending-inventory-item-*` keys, called
> from `ScanPage.tsx:453`, inventory items only — and syncing with
> `Promise.allSettled` (`sync-manager.ts:55`), so it has **no** head-of-line
> blocking.
>
> **What this changes.** The cutover angle disappears entirely: an empty queue has
> nothing to replay, so moving `REACT_APP_API_URL` cannot jam it. The task 3.7
> mitigation is correspondingly downgraded from required to precautionary. The code
> defect below is still really in the code and would bite the moment anything calls
> `addOperation` — so it is a latent defect in dormant code, not a user-facing risk.
> Tracked as **#480**, with this correction posted there.
>
> **Why it was missed, and the lesson.** §G asked, per call site, *does this URL
> follow `API_BASE_URL`?* — and never asked *does anything call this?* That second
> question is exactly what Findings 16 and 22 turned on, and what #471 turned on.
> This is now the fifth instance in this audit of **a well-tested module with no
> production importer**, where the passing tests are precisely what make it look
> maintained. Reachability is not a special case in this codebase; it is the default
> thing to check.
>
> The material below is retained as the description of the latent defect.

§G8 recorded that `lib/offline-sync.ts` replays queued writes against whatever
`API_BASE_URL` is current, so a cutover mid-queue retargets already-queued writes.
That was accurate but stopped short: it named the risk and proposed `keep` without
saying what must be done about it. This finding supplies the missing half.

**The mechanism.** `processQueueOperations` (`:213-243`) iterates the queue and, on
any failure, logs to Sentry and `break`s at `:239`. `removeOperation` is called only
on success (`:222`). So a failed operation stays at the head of the queue and every
operation behind it stays queued too.

There is no escape hatch for a permanently-failing operation:

- No per-operation attempt counter. `OfflineOperation` (`:9-14`) stores `action`,
  payload and `timestamp` — no `attempts` field.
- No queue size cap and no age eviction. The queue is a `localStorage` array
  (`:22`, `:170`) that only shrinks on success.
- `performSyncWithRetry`'s three retries (`:277`) are retries *within one sync run*,
  and `:294-295` exits early if any operation succeeded — "Some operations synced,
  not retrying failed ones". A poison operation at the head is retried three times
  per sync cycle, forever, and never expires.

The only drain is `clearQueue()` (`:418-419`), which deletes the whole queue and
every unsynced write in it.

**Why the cutover is the trigger.** Today a poison operation needs an unlucky 4xx —
a validation failure, a record someone else deleted, a permission revoked between
queueing and sync. At cutover, every queued operation retargets at once, and the
question becomes whether the Worker accepts each one. It will not accept all of
them: 2.1 has 89 consumed Express routes needing Worker equivalents, and task 3.1.d
already records that **six of the eight credit-claim endpoints the frontend calls
have no Worker route**. A queued write to a route the Worker does not serve fails,
and takes the rest of that user's queue with it.

**One correction to how this was reported.** The likely cutover failure is a
**missing Worker route**, not a schema change — the Postgres schema is shared by
both backends and Phase 1 already adopted it in production. That distinction
matters because it makes the risk enumerable rather than open-ended: it is bounded
by the §A rehoming list, and it shrinks to zero as 3.1 completes.

**Two separable problems, and they want different homes.**

1. **Head-of-line blocking is a pre-existing defect, independent of this change.**
   It reproduces today with any persistent 4xx and survives Phase 4 untouched. By
   the discriminator established at #460, that is an **issue**, not spec-only work:
   a per-operation attempt cap, then drop-with-report to Sentry or move to a
   dead-letter list the user can see.
2. **The cutover-specific exposure belongs to this change** and is recorded as the
   task 3.3 / 4.x mitigation below.

**Proposed cutover mitigation**, in order:

1. **Sequence the cutover behind 3.1**, so no consumed Express route lacks a Worker
   equivalent when `REACT_APP_API_URL` moves. This is the real mitigation — the
   other two only limit the blast radius if it is skipped.
2. **Drain before the switch.** On the first load after cutover, and before
   repointing, trigger a sync while Express is still serving and confirm the queue
   is empty. Note the limit honestly: the queue lives in each browser's
   `localStorage`, so a user who is offline or does not open the app across the
   cutover window cannot be drained. This reduces exposure; it does not eliminate it.
3. **Do not reach for `clearQueue()` as the mitigation.** It discards unsynced
   customer writes silently. If it is used at all it needs an explicit,
   user-visible decision, not a quiet call during cutover.

**A note on why this was missed.** §G was built by asking one question per call
site — does this URL follow `API_BASE_URL`? — which is the right question for 13 of
the 14 rows. G8 answers "yes" and is, on that question, correct. What the question
does not surface is that this call site is the only one that *defers* its requests:
everything else fails in front of a user who can retry, and the queue fails later,
alone, behind a `break`. Deferred execution deserves its own question in an audit
of a cutover, and §G did not ask it.

Frontend user-facing strings were swept the same way. `TrialFAQ.tsx:67` is the only
component that names an API route in copy shown to users; the two other matches
(`useOrgBootstrap.ts:25`, `DashboardPage.tsx:29`) are JSDoc comments above the
functions that call those routes, not instructions to a user.

**A separate defect found by the same sweep, unrelated to this change.** The FAQ
offers two ways to export before a trial expires. **"Settings → Export Data" does
not exist.** `frontend/src/pages/SettingsPage.tsx` contains no export capability —
the only match for "export" in the file is the `export function` keyword at `:31`.
So a trialing customer about to lose access is offered one path that does not exist
and one that requires a bearer token and a terminal. That is independent of this
migration and survives Phase 4, so by the #460 discriminator it is **issue** work,
not spec work. **Filed as #482.**

**What to carry forward.** When a route has no code call site, that is the beginning
of the enquiry, not the end. Ask what else could be calling it: an external service,
a documented instruction, an operator runbook, a scheduled job. This is the second
methodological hole Phase 2 found in itself — Finding 25 was the first (§G never
asked whether anything *called* the module it was auditing) — and both were found by
a reviewer, not by the gates. Neither `check-audit-columns.js` nor
`verify-audit-manifest.js` can catch a uniformly-filled column that is uniformly
wrong; that limit is stated at §B and these two findings are what it looks like in
practice.
